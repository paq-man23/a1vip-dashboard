# Al conversational dashboard assistant

Deploy `index.ts`, `handler.mjs`, `planner.mjs`, `ticketmaster.mjs`, `seatgeek.mjs` and `event-search.mjs` together. Set `OPENAI_API_KEY` in Supabase Dashboard → Edge Functions → Secrets; never put a key in frontend files or GitHub. Optional `OPENAI_MODEL` defaults to `gpt-4.1-mini`. OpenAI API billing/quota must be active. No key means dashboard search, guidance, draft preparation and summaries continue; conversational requests explicitly report configuration is needed. In Al settings, Check AI connection checks key presence; a conversational question verifies actual provider access.

The endpoint validates the bearer token through Supabase Auth, current staff membership, disabled status and the dashboard activity session before using the provider. It retains the existing `verify_jwt:false` deployment because it performs its own Auth checks. The provider key stays on the server. Auth and record reads use the caller's token, never a service-role credential.

The current typed request, up to six prior user requests and the current public event-search filters are sent to OpenAI Responses with `store:false`. This does not promise zero provider retention: OpenAI's applicable API data policy still applies. No database snapshots, model-generated result messages, tool definitions or client-supplied system instructions are forwarded. Records, summaries, account names, links and vault entries are not automatically added to prompts. A name explicitly typed by a user is part of their request. Model responses are validated structured proposals for an allowlisted action; the model never receives database credentials or executes code. Every action rechecks current browser permissions; writes still use existing reviewed UI flows and database RLS.

Natural requests can search contacts, invoice/PO history by event or customer, saved trips and letters, navigate, prepare contact-filled invoice/PO drafts, propose duplicate-checked links, answer dashboard questions, and request deterministic summaries with year/document/payment filters. Summaries separate invoices and POs, honor hotel room quantities and saved credits, and exclude void records from financial totals. No email sending, payment actions, arbitrary deletion, automatic saving or vault access is exposed. Existing draft/open confirmations remain.

A bounded per-instance burst guard limits model requests to 12/minute/user. This is not a distributed spend cap; configure the OpenAI project's budget and provider rate limits for global control. Input/output sizes and upstream timeouts are bounded. Provider errors are sanitized. Conversation context stays in memory and clears on New Chat, sign-out, password recovery or access change. Late responses are discarded after those events.

Voice is opt-in per chat, starts only on a microphone click and fills a reviewable transcript without submitting. Browser speech recognition may use the browser vendor's remote service; the UI discloses this before opt-in. Closing, hiding, clearing or signing out stops listening. Unsupported browsers offer typing/keyboard dictation. Vault remains a separate screen without Al.

Validation: `npm test`, including model-request privacy, rejected permissions, missing-key behavior, provider failures, stale-response cancellation, voice opt-in and deterministic financial summary fixtures. Real provider access additionally requires an authenticated dashboard conversation after secret setup.

## Ticketmaster Discovery

Deploy all six function modules together. Save the approved Ticketmaster **Consumer Key** as `TICKETMASTER_API_KEY` in Supabase Edge Function secrets. Consumer Secret and OAuth callbacks are not used by Discovery. Key presence is reported through the authenticated Al settings check; an actual search verifies access. The API key never reaches the browser or OpenAI. All event requests require the same Auth, staff and activity-session checks as chat.

Al accepts natural event questions with artist/team/venue, city and date/range. The model produces only validated search filters; returned provider data is rendered directly and never sent back to OpenAI. The explicit `find events Knicks` command also works without an OpenAI key. Results use event-local date/time, preserve TBA flags and event status, show public event links, and label optional published price ranges as event-level information with unconfirmed fees. No section, row, seat quantity, live availability or resale quote is invented. Results include source/check time and pages of ten within Discovery's deep-paging limit. An absent/rejected key, provider limit, empty search or timeout gives an explicit message.

Natural event conversations now request missing location/month before calling the connected event providers, with explicit Any Location / Any Month options. The planner is instructed to normalize clear artist typos and clarify ambiguous names. Its validated schema includes separate `city`, `stateCode`, `countryCode`, `anyDate` and `anyLocation` fields. A deterministic normalizer recovers state names/abbreviations and supported city shorthand from event keywords or a misplaced city field; it preserves performer names such as Florida Georgia Line. For example, Olivia Rodrigo Florida becomes keyword Olivia Rodrigo + stateCode FL + countryCode US.

Only the previous public event-search filters are added to model context; no result records or customer data are forwarded. The backend carries artist/location/date across event follow-ups, asks only for missing details and queries after selection or explicit any-scope choices. Direct `find events` searches remain available as immediate lookups; guided continuation buttons request the same refinement checks. Empty results retain the exact scope and offer user-selected widening.

## Combined SeatGeek and Ticketmaster search

Save SeatGeek developer credentials as server-only `SEATGEEK_CLIENT_ID` and, if issued, `SEATGEEK_CLIENT_SECRET` in Supabase Edge Function secrets. Obtain access from https://developer.seatgeek.com/. The adapter implements the official legacy v2 event API documented at https://seatgeek.github.io/, using Basic authentication. Availability, account eligibility and live credentials must be verified with SeatGeek; local tests use mocked responses and do not establish live account access. No free tier or individual ticket-listing access is promised.

Searches call both configured providers concurrently with the same event/location/date scope. Missing credentials and individual provider errors are shown separately; one successful source remains usable when the other fails. Each provider supplies up to ten events per page. Cross-provider cards combine only when known local date/time, venue, city and event identity agree, with additional safeguards for VIP/package/parking products. Uncertain matches stay separate. Merging is limited to the current page; the displayed combined count is a page count, not a catalog-wide unique total. Per-provider counts remain visible.

Each source retains its own link, status, check time and price information. Ticketmaster published price ranges and SeatGeek event-level lowest/average/highest statistics are not equivalent-seat quotes and are never ranked as a cheapest ticket or best deal. SeatGeek missing prices and zero listing counts stay explicit; currency is shown only when provided and otherwise marked unknown. Fees, quantities and section/row availability require confirmation on the provider. API credentials and raw responses never reach OpenAI or the browser.
